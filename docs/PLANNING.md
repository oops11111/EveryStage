# EveryStage 产品规划讨论纪要

## 1. 产品定位

Windows 内网投屏/扩展显示程序，支持图片、视频、音频、可编辑文档在扩展屏（LED/投影）上展示，并支持接收内网其他 Windows 设备投放的内容。

---

## 2. 角色模型

| 角色 | 定位 | 特点 |
|---|---|---|
| **终端机** | 常驻服务，绑定扩展屏 | 开机自启、后台监听、纯播放器角色，不适配任何远程内容格式 |
| **投屏机** | 临时使用的轻量工具 | 用时打开，选择目标终端机，发起后即可关闭 |

- 决策权集中在终端机：投屏机只负责"申请显示"，由终端机决定是否输出到扩展屏。
- 一台机器同一时刻通常只有一个投屏请求（多请求为少数场景）。

---

## 3. 内容渲染责任划分

**原则：谁输出谁负责。**

| 内容来源 | 渲染位置 | 说明 |
|---|---|---|
| 终端机本地文件 | 终端机 Content Engine 直接解析渲染 | 图片(WIC)、视频(Media Foundation)、PDF(PDFium)、Office文档(接入WPS接口，支持编辑/翻页) |
| 投屏机内容 | 投屏机本地渲染后屏幕捕获推流 | 终端机只做视频流解码显示，不关心源格式 |

- 文档"可编辑、翻页"：编辑动作发生在投屏机本地，终端机只镜像显示，**不做反向控制通道**。
- 投屏机捕获方式：**全屏捕获**（非应用内窗口捕获），需在投屏器界面明确提示"将投放整个屏幕"。

---

## 4. 网络与传输技术方案

### 4.1 关键指标优先级
**延迟 > 画面稳定 > 分辨率精确还原**（分辨率跟随原始，网络拥塞时自动降级）

### 4.2 技术选型
| 环节 | 方案 |
|---|---|
| 屏幕捕获 | Desktop Duplication API (DDA) |
| 视频编码 | H.264 硬件编码（NVENC/QuickSync/AMF），禁用B帧，零延迟预设，CBR码率控制，短GOP |
| 传输协议 | UDP + RTP，基于 WebRTC 媒体传输能力（NACK/FEC丢包恢复 + 拥塞控制），不使用 WebRTC 的 NAT穿透部分（内网不需要） |
| 帧率策略 | 动态帧率：静止画面低帧率(5-10fps)省带宽，变化时立即跟上 |
| 解码渲染 | Media Foundation硬件解码(DXVA) → D3D11纹理直出 → DXGI SwapChain呈现，全程零拷贝，不用WPF/WinForms常规控件绘制 |
| 音频输出 | WASAPI，音频时钟为主时钟，视频帧同步音频时钟 |

**明确排除**：LibVLCSharp（VLC类通用播放器不满足实时低延迟同步需求）

### 4.3 技术栈
C#，视频处理链路需注意GC暂停风险（用 Span/非托管内存/对象池），WebRTC生态候选：SIPSorcery。

### 4.4 技术验证Demo（开发前置）
范围：本地/模拟推流 → 硬解码 → D3D11纹理 → SwapChain显示（不含采集编码、网络传输、UI）

验收标准：
- 端到端延迟 ≤30-50ms
- 帧率无掉帧（CBR测试流下）
- 分辨率1080p/4K均可跑通
- 音画偏差 ≤1帧
- 连续播放1小时无内存泄漏

## 5. 显示输出实现

**方案：无边框全屏窗口**（非虚拟显示驱动IDD），理由：开发难度低、部署简单、兼容性好，产品需求不依赖系统级"真实显示器"特性。

要点：
- `SetWindowPos` + `HWND_TOPMOST`，避免任务栏/其他窗口遮挡
- 多显示器精确定位（`EnumDisplayMonitors`）
- 适用于专用展示屏场景（LED/投影，无人直接操作）

---

## 6. 数据结构

```
方案 Scenario（可保存/切换，如"周一晨会方案"）
  └─ 活动 Activity（可拖拽排序、可折叠展开，如"开场介绍"）
       ├─ 播放模式：顺序自动 / 手动点选（活动级默认值）
       └─ 文件 File（可多个，缩略图展示）
            ├─ 类型：图片/视频/音频/文档
            ├─ 播放模式（可覆盖活动默认）
            ├─ 停留时长（图片/文档）
            ├─ 淡入/淡出时长 + 音量是否随渐变（视频/音频）
            ├─ 播放完成后动作：自动下一项/循环/停留等待
            └─ 允许手动跳过
```

**音频特殊性**：无可视化画面内容，需单独分类；可作为"背景音频"叠加在其他视觉内容之上播放，不占用主队列顺序位；投屏时扩展屏显示内容可配置（波形动效/默认背景图/纯黑）。

---

## 7. 内网设备管理

- **发现**：局域网UDP广播/mDNS
- **配对**：首次需接收端确认（弹窗/PIN码），配对后记住设备指纹
- **信任策略**：已配对设备可设"信任模式"（自动接受）或"需手动确认"
- **权限分离**：`允许被投放` 与 `允许被监看` 独立开关，不因配对而默认互相授权

---

## 8. 终端机 UI 信息架构

### 8.1 整体布局
- **左侧固定竖向功能区**：投屏开关（滑动开关，非按钮）+ 断（独立按钮）+ 文件/活动/设备/设置（导航图标）+ 连接状态
- **右侧主内容区**：随导航切换四个面板

### 8.2 四个主面板
| 面板 | 内容 |
|---|---|
| 文件（默认首页） | 缩略图网格，分类标签（全部/图片/视频/文档/音频），音频以横向播放条展示（含播放/进度/音量/循环/独立投屏按钮） |
| 活动 | 方案选择器（切换/另存为/新建）+ 活动列表（可折叠、拖拽排序、滚动）+ 输出状态条 |
| 设备 | 已配对设备列表（信任状态）+ 发现新设备区域 |
| 设置 | 二级分类：通用 / 显示 / 播放行为 / 网络与设备 / 关于 |

### 8.3 悬浮预览窗
- 仅在扩展屏有输出时出现，无输出时不存在
- 内容：LIVE标识、缩略画面预览（GPU降采样拷贝，非独立渲染）、进度信息、四个快捷按钮（上一项/暂停/下一项/切断）
- 支持拖动记忆位置、置顶开关、意外关闭后从主面板召回

### 8.4 关键状态区分
- 本地播放/预听状态 与 投屏输出状态 相互独立（如音频可"本地暂停+扩展屏继续投屏"）

## 9. 投屏开关与断开逻辑

### 9.1 投屏开关（替代原"一键投屏"按钮）
- **开启**：点击文件 = 播放并立即投屏到扩展屏；活动流程自动播放同样受此开关约束
- **关闭**：点击文件 = 仅本地预览播放，不推送扩展屏
- 开关状态与"断"相互独立：断开后开关仍保持开启，下次点击文件立即重新投屏
- 设备投屏请求不受此开关影响（接受请求本身即是一次明确操作）
- **原"单击/双击触发"设置项作废**，由开关模式统一替代

### 9.2 "断"的精确行为
"断" = 一键停止当前扩展屏输出内容，**将该屏幕控制权交还给 Windows**（恢复到程序介入前的原始状态：桌面、壁纸或其他已存在窗口），而非切换到程序自定义的待机画面。

- **画面层**：关闭/隐藏程序的覆盖输出窗口，不动底层其他窗口（覆盖式架构下，底层窗口从未被最小化或关闭，天然保留原有现场）
- **响应速度**：输出窗口与D3D11 SwapChain建议预先创建并常驻、仅隐藏/显示切换，而非每次销毁重建，保证"投/断"切换的即时响应
- **底层应用现场保留的局限**：若被覆盖的是原本占用该屏幕的全屏应用，其失焦后的行为（暂停/退出全屏等）由该应用自身逻辑决定，程序无法保证其可完全恢复

### 9.3 音频接管与恢复
投屏期间需**独占终端机上所有音频**（不仅限于扩展屏对应设备），避免声音冲突：

- **投屏开始**：对终端机上所有正在活动的音频会话，优先发送系统媒体键（`VK_MEDIA_PLAY_PAUSE`）使其暂停在当前位置；若目标程序不响应媒体键，则退回**静音**作为兜底
- **断开时**：再次发送媒体键使暂停的内容从原位置继续播放；被静音的会话恢复原音量
- 优先级：**媒体键暂停 > 静音兜底**，两段式处理，不是二选一

## 10. 终端机整体状态流程

```
开机启动
   │
   ▼
待机中（后台监听，开机自启，常驻状态）
   │
   ├──→ 投屏开关开启时点击文件 ──┐
   │                              ├──→ 扩展屏输出中 ──→ 断 ──↻ 返回待机
   └──→ 接受设备请求 ────────────┘
```

- **待机中**是常驻默认状态，两条触发路径（本地文件/设备请求）独立发生，但汇入后行为统一：都受"断"控制（交还Windows控制权），都会在悬浮预览窗中显示。
- **关闭程序**不属于主操作循环，是待机状态下的次要分支（托盘菜单主动退出），不影响上述循环。

## 11. 交互细节

**拖拽添加**：拖到活动条目上=追加；拖到活动之间空隙=新建活动并放入，用位置区分意图，不弹窗确认。

**批量选择**：`Ctrl/Shift+点击` 或长按进入选择模式；选中后悬浮工具栏出现（加入活动/统一设置属性/删除），跨类型选中时屏蔽不适用的属性项。

**异常提示**：右下角Toast通知栈，按严重程度分色（红=严重/黄=提示），涉及播放的异常需带可执行按钮（重试/移除），非关键提示不强加按钮。

---

## 12. 投屏机（轻量工具）UI

- 待机态：目标终端机列表（已配对直显）+ "开始投屏"大按钮 + 隐私提示（将投放整个屏幕）
- 投屏中态：投屏对象+时长+隐私提醒条+"停止投屏"按钮
- 单一任务导向，不做复杂功能堆叠

---

## 13. 视觉设计

**风格**：磨砂玻璃（建议用Windows原生 Acrylic/Mica API 实现，避免自行实时高斯模糊占用GPU资源，与视频渲染主线程抢资源）

**三套可切换主题**：
| 主题 | 强调色 | 适用场景 |
|---|---|---|
| 白色系 | 科技蓝 | 明亮环境，日常模式 |
| 黑色系 | 科技蓝 | 常规室内环境，长时间使用不刺眼 |
| 高科技系 | 蓝色发光+网格背景 | 展会/发布会等需要视觉冲击力的场合 |

统一结构：面板圆角、间距、字重层级一致，仅换配色参数（accent色/背景渐变/玻璃透明度/发光强度），主题切换不改变布局逻辑。

## 14. 部署、安全与运维

### 14.1 本地文档渲染引擎
本地Office文档（PPT/Word/Excel）**接入WPS接口**，采用 **COM互操作**方式（而非纯渲染SDK）——因为"文档可编辑"需求要求直接操控WPS对象模型（打开/翻页/编辑/保存），渲染型SDK通常不具备编辑能力。

代价与风险需提前规划：
- 每台终端机需安装并授权一份WPS（License成本+部署工作量）
- COM自动化依赖WPS进程本身稳定性，需做静默模式（隐藏UI）+ 预案处理意外弹窗（更新提示/授权提醒）
- 需锁定测试通过的WPS版本，避免自动升级导致COM接口行为变化

### 14.2 更新策略
**禁用热更新**——版本更新需要重启程序完成，不支持投屏过程中后台静默升级替换运行中的模块。

### 14.3 安全性
- **不加密**：内网传输明文，不引入加密开销
- **不设账号登录体系**：不做用户身份管理，配对关系基于设备而非账号

### 14.4 日志与诊断
**需要**——终端机作为无人值守展示设备，需完善的本地日志与自诊断机制。分三类物理独立存储，便于按问题类型定位：

| 日志类型 | 记录内容 | 用途 |
|---|---|---|
| 文件操作日志 | 本地文件导入/删除、方案/活动的创建/修改/删除、播放属性变更 | 追溯内容误操作 |
| 播放/投屏记录 | 每次播放开始/结束时间、播放内容、触发方式（开关/活动自动）、异常中断及原因 | 复盘某时段展示内容 |
| 设备连接记录 | 配对/取消配对、连接建立/断开时间、连接质量指标（丢包率/延迟）、断开原因 | 排查网络问题 |

日志按天滚动 + 自动清理旧日志，避免无人值守设备日志无限增长占满磁盘。

### 14.5 授权机制
**不使用许可证/License校验**，不限制安装数量（注：WPS自身的License与本机制无关，见14.1）。

## 15. 开发排期建议

按依赖关系与风险等级分阶段：

| 阶段 | 内容 | 风险/说明 |
|---|---|---|
| 0 | D3D11零拷贝渲染管线技术验证Demo | **最高优先级，不可跳过**，后续开发建立在此结论之上；1-2周；团队缺DirectX经验需评估外部支持 |
| 1 | 终端机主程序框架（覆盖式窗口、投屏开关/断状态机、数据持久化）+ 本地内容引擎（图片/视频/PDF，成熟技术风险低）+ WPS COM互操作验证（风险仅次于阶段0，需尽早分配专人验证） | 可与阶段0部分并行 |
| 2 | 投屏传输链路：屏幕捕获(DDA)→H.264编码→RTP传输→解码渲染整合，投屏机轻量工具同步开发 | 依赖阶段0验证通过；第二大技术风险区 |
| 3 | 设备发现/配对（mDNS/UDP、信任策略）+ 音频接管（媒体键暂停+静音兜底） | 相对独立，可与阶段2并行 |
| 4 | UI完整开发：四大面板+悬浮预览窗+交互细节 | **已有高保真原型可直接对照实现，确定性最高、风险最低**，不依赖阶段0/2完成即可开工 |
| 5 | 视觉主题（三套配色+磨砂玻璃）+ 日志诊断系统 | 可叠加在阶段4基础上，工作量较小 |
| 6 | 联调、部署打包、验收：逐项验证第16章待确认事项，确定安装包方案，试点部署 | 收尾阶段 |

**关键依赖链**：阶段0→阶段2（传输链路）是主线瓶颈；WPS COM验证是另一条独立但同样卡整体进度的支线；UI（阶段4）基本不卡别人也不被别人卡，可最早启动、最晚收尾对齐整体联调。

## 16. 待确认/待验证事项

1. D3D11零拷贝渲染管线技术验证Demo（详见第4.4节验收标准）
2. 团队 DirectX / Media Foundation 开发经验是否需要外部支持
3. 音频"背景轨道"与视觉内容叠加播放的具体互斥/共存规则细化
4. 活动列表规模较大时的性能表现（虚拟滚动等优化）
5. 悬浮预览窗与主面板预览缩略图的召回交互细节
6. 媒体键（`VK_MEDIA_PLAY_PAUSE`）对各类第三方播放器的实际兼容率需要实测，确定静音兜底的触发比例
7. 覆盖式全屏窗口对底层全屏应用（失焦后行为）的影响范围需要实测覆盖常见软件
8. 日志文件的具体存储格式（结构化JSON vs 纯文本）与是否提供可视化诊断面板待细化
9. WPS COM互操作的静默模式实现与异常弹窗预案需要实测验证（不同WPS版本行为可能不同）
10. 每台终端机部署WPS的License采购与批量部署方式待与WPS官方/代理确认
