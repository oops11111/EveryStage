# 监看与多终端产品策略

状态：已决策，作为后续协议与 UI 实现边界。

## 1. “监看”的产品定义

监看是**只读运行状态查看**，不是远程桌面，也不传输扩展屏画面或声音。允许展示：

- 终端名称、在线状态、应用版本和最近心跳时间；
- 待机/输出中、当前来源（本地内容或投屏设备）；
- 当前内容的文件名与媒体类型，不返回本地绝对路径；
- 已运行时长、视频帧数、接收字节数、丢包率、延迟及最近错误；
- 扩展屏是否连接、当前分辨率和绑定显示器名称。

不允许展示或执行：屏幕截图、音视频预览、文件内容下载、键鼠控制、播放控制、修改设置。
这些能力如果未来需要，必须作为新的显式权限和协议设计，不能复用 `AllowMonitor`。

## 2. 权限与安全

- `AllowMonitor` 与 `AllowCast` 保持独立，配对成功不默认开启任何一项。
- 监看请求和响应必须使用配对设备密钥认证，并经过防重放校验。
- 未配对、密钥版本过旧、权限关闭或认证失败时，不返回任何运行状态。
- 设备被取消配对或密钥轮换后，旧密钥立即失去监看权限。
- 监看默认按需拉取；监看面板打开时最多每 2 秒刷新一次，关闭后停止请求。
- 终端记录监看会话的开始、结束、请求设备和拒绝原因，不记录每次轮询，避免日志泛滥。

## 3. 多终端策略

首个正式版本采用以下限制：

- 一台投屏机同一时间只能向一台终端机投屏。
- 一台终端机同一时间只接受一个投屏来源。
- 已在投屏的终端收到第二个开始请求时返回 `busy`，不得静默抢占。
- 操作者必须先停止当前会话，再选择另一台终端；不提供“一键广播到多台”。
- 投屏机可同时监看多台已授权终端，但监看不占用投屏会话名额。
- 本地内容播放与远程投屏仍共享一个输出位；新来源不得自动覆盖当前输出。

不在首版支持多目标投屏，原因是它会同时引入多路发送背压、终端间状态聚合、部分失败处理、
不同分辨率协商和更高的编码/网络资源成本。以后若有明确业务需求，应新增独立的“终端组/广播会话”
能力，不在现有单目标 `LiveCastSession` 上隐式扩展。

## 4. 协议实现边界

后续实现应新增版本化消息，而不是扩充现有心跳的含义：

- `monitor_request`：请求一次状态快照；包含请求编号。
- `monitor_status`：返回上述白名单字段；包含请求编号和采样时间。
- `cast_start_result`：明确返回 `accepted`、`busy`、`not_allowed`、`incompatible`。

三类消息均需遵循现有认证、时间窗、防重放和协议版本规则。`monitor_status` 不复用
`CastStatusMessage`：后者是活动投屏会话中的反向确认，生命周期和受众均不同。

## 5. UI 决策

- 投屏机待机页保留单选终端列表；开始投屏按钮只作用于当前选中项。
- 增加独立“监看”页，以卡片列表展示多台终端状态，不把监看塞进投屏中页面。
- `busy` 在目标行内明确显示“正在被其他来源占用”，不自动重试或排队。
- 终端设备面板继续提供“允许被投放/允许被监看”两个独立开关。
- 在真正实现监看协议前，现有“监看功能尚未实现”提示继续保留。

## 6. 验收条件

- 权限关闭、未配对、旧密钥、篡改、重放请求均无法取得状态。
- 同一投屏机切换目标必须先结束原会话；第二来源不能抢占忙碌终端。
- 同时监看多台终端不会启动媒体流，也不会改变任一终端的播放状态。
- 监看面板关闭后停止轮询；断网和终端离线在 10 秒内显示为离线。
- 日志能够回答“谁在何时开始/停止监看”和“为何被拒绝”。
